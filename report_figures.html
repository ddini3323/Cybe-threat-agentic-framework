CTI Agentic System — Report Figures

All 7 figures referenced in the project report, rendered as crisp vector diagrams. Use the sidebar to navigate. Screenshot each figure card for insertion into the report at the labelled positions.

Figure 1.1

System Overview — Five-Agent CTI Pipeline

High-level architecture showing how raw threat data from three input channels flows sequentially through five AI agents — Ingestion, Enrichment (with ChromaDB RAG), Pattern Discovery, Mitigation Generation, and Validation — to produce actionable intelligence displayed on the SOC Dashboard. The self-learning loop stores enriched events back into ChromaDB, improving future retrievals.

Figure 1.1: System Overview — Five-Agent CTI Pipeline. Raw threat data enters from three independent input channels and is processed sequentially through five AI agents before results are presented on the SOC Dashboard.

DFD Level 0 — Context Diagram

The context diagram (DFD Level 0) shows the system as a single process surrounded by four external entities. It defines the system boundary and all data flows crossing that boundary: threat submissions from the analyst, live feed events, knowledge-base queries to MITRE ATT&CK, and mitigation reports delivered to the SOC Dashboard.

Figure 4.2: DFD Level 0 Context Diagram — the CTI Agentic System (central circle) surrounded by four external entities with labelled data flows crossing the system boundary.
Figure 4.3

DFD Level 1 — Internal Pipeline Flows

Expands the single system circle into five internal processes (P1–P5), each mapping to one AI agent. Data flows are shown between processes and two persistent data stores: D1 (ChromaDB, holding MITRE ATT&CK techniques and enriched threat history) and D2 (Pattern Store). Analyst and Feed input enters at the top; validated output reaches the SOC Dashboard at the bottom.

Figure 4.3: DFD Level 1 — the five internal processes (P1–P5) with data flows and two persistent stores (D1: ChromaDB and D2: Pattern Store). The store-back arc from D1 shows the self-learning loop.
Figure 5.1

ER / Data Model Diagram

Shows the four core Pydantic data entities and their relationships. ThreatEvent is created by the Ingestion agent; Enrichment extends it to EnrichedEvent; Pattern Discovery clusters events into ThreatPattern; Mitigation Generation produces a MitigationAction for each pattern. Primary keys (PK) are generated as MD5 hashes or UUID strings; foreign keys (FK) maintain referential integrity through the pipeline.

Figure 5.1: ER / Data Model Diagram — four Pydantic entities with field definitions, PK/FK markers, and three inter-entity relationships: enriches, clusters into, and triggers.
Figure 5.2

Sequence Diagram — Threat Processing Flow

Chronological message sequence for a single threat submission via POST /api/ingest/instant. Solid arrows are synchronous calls; dashed arrows are return values. The self-call loop on the Enrich lifeline represents the local LLM inference step (llama3.2:3b), which is offloaded to a thread via asyncio.to_thread() to avoid blocking the event loop. Store-back writes the enriched event to ChromaDB for the self-learning loop.

Figure 5.2: Sequence Diagram — 15 messages between Analyst, FastAPI orchestrator, and five agents for a single threat submission. Dashed lines are return values; the self-loop on Enrich represents local LLM inference.
Figure 5.3

Activity Diagram — Pipeline Decision Logic

Complete end-to-end activity flowchart for a single threat event through the pipeline. Four key decision gates are shown: duplicate detection, enrichment confidence threshold, severity threshold, and validation pass/fail. Side branches capture discarded, low-confidence, low-severity, and rejected events. Only events that clear all four gates are published to the SOC Dashboard.

Figure 5.3: Activity Diagram — complete pipeline decision logic from START to END. Four decision gates (duplicate, confidence, severity, validation) filter events; only those passing all gates are published to the SOC Dashboard.
