5.2 Module Description
-----------------------

5.2.1 Ingestion Agent
~~~~~~~~~~~~~~~~~~~~~~
Responsible for all data ingestion and normalization. Four data input methods are available, and the agent polls the directory data/input/ on every iteration cycle:

  a) CSV data normalization:
Utilizes pandas library to load files. Fieldnames such as "indicator," "ioc," "value," "ip," and "url" can be utilized. The description field is extracted from the raw content of the row if not present. 
     Each row is associated with one ThreatEvent object.

  b) JSON data normalization:
Supports JSON arrays and objects. Fieldnames include "description," "text," "content," "raw," and "message." One ThreatEvent object will be created for each array entry.

 d) Get URL:
Makes feed URLs passed through HTTP GET for EXTERNAL_FEEDS.
       The response content is converted to a ThreatEvent, and it is treated as unstructured free text.

  d) Deduplication 
The previously encountered information is tracked using two sets, namely processed_files and processed_feed_ids. Duplicate prevention is carried out using MD5 of the source and indication.

  ThreatEvent Schema:
    event_id   : MD5(source + data)
    timestamp  : ISO 8601 ingestion time
    source     : origin (filename, URL, or 'manual')
    event_type : ThreatType enum (IP/URL/Domain/Hash/Email/CVE/Unknown)
    raw_text   : human-readable description
    indicator  : extracted indicator value
    severity   : SeverityLevel (1-5)
    raw_data   : dict of original fields


5.2.2 Enrichment Agent
~~~~~~~~~~~~~~~~~~~~~~~
employs a three-stage RAG + LLM process for adding semantic understanding to every ThreatEvent [25][14].

Step 1: Context of MITRE RAG
employs the text of the event itself to query CTIRetriever.get_mitre_context() that returns the top 5 MITRE ATT&CK methods whose cosine similarity is ≥ 0.35. In order to avoid any noise, methods that have lower similarities are not included.

Step 2: Previous Dangers Background
queries up to three similar events from the threat_reports collection stored in ChromaDB via get_similar_threats_context(), enabling the LLM to form conclusions based on analogous past incidents.

Step 3: Extraction of LLM
via Ollama, an input template (system role + MITRE context + previous dangers background + event information + JSON schema) is passed to llama3.2:3b.
    The LLM extracts:
      iocs[]           : list of {type, value} pairs
      cves[]           : CVE identifiers
      ttps[]           : MITRE technique IDs (T####.###)
      mitre_tactics[]  : MITRE tactic IDs (TA####)
      attack_stage     : kill-chain stage name
      threat_category  : categorical label
      malware_family   : identified malware or threat actor
      attack_vector    : initial access method
      affected_assets[]: asset types affected
      enrichment_confidence: float 0.0-1.0

  Step 4 - Store-back:
    If enrichment_confidence > 0.3, the EnrichedEvent is persisted into
    ChromaDB threat_reports collection for future retrieval (self-learning
    loop).


5.2.3 Pattern Discovery Agent
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Groups enriched events into ThreatPattern objects using a multi-factor
weighted similarity score:

  Similarity = (TTP_jaccard * 0.4) + (malware_match * 0.3)
             + (vector_match * 0.2) + (asset_jaccard * 0.1)

  Where:
    TTP_jaccard    = |A.ttps ∩ B.ttps| / |A.ttps ∪ B.ttps|
    malware_match  = 0.3 if same malware_family, else 0
    vector_match   = 0.2 if same attack_vector, else 0
    asset_jaccard  = Jaccard of affected_assets sets

  A pair of events joins the same pattern when similarity >= 0.7.
  A greedy merge assigns each event to the closest pattern above threshold
  or seeds a new one if no match exists.

  ThreatPattern Schema:
    pattern_id      : UUID
    pattern_name    : descriptive name derived from TTPs/malware
    event_ids[]     : member event IDs
    common_ttps[]   : TTP IDs present in >= 50% of member events
    common_iocs[]   : IOCs shared across member events
    affected_systems[]: all unique asset types
    confidence      : min(0.5 + event_count * 0.1, 0.95)
    severity        : maximum severity of member events


5.2.4 Mitigation Agent
~~~~~~~~~~~~~~~~~~~~~~~
employs the technique of chain-of-thought prompting [27], which allows it to offer recommendations that are organized and actionable, in three clear steps:

  1. Threat Mechanics Assessment
The LLM describes how the threat gains access, what paths it follows laterally, and what its aims are.

  2. D3FEND Mitigation Selection:
The LLM correlates the threat with the defense mechanisms of MITRE D3FEND [29]:
      network isolation (D3-NI), incoming traffic filtering (D3-ITF), outgoing traffic filtering (D3-OTF), user accounts management (D3-UA), MFA, endpoint detection (D3-EDR), process analysis (D3-PA), and process monitoring (D3-PM).

  3. Minimum Effective Defense Strategy
In order to mitigate the detected danger, the LLM proposes the minimum number of relevant mitigation strategies needed.

  MitigationAction Schema:
    title        : short action name
    description  : explanation of the mitigation
    steps[]      : 3-5 specific actionable steps
    sample_rule  : example firewall/IDS/SIEM rule
    reasoning    : chain-of-thought explanation
    mitre_d3fend[]: list of D3FEND technique IDs
    priority     : integer 1-5 (5 = most urgent)
    status       : PENDING_REVIEW | APPROVED | REJECTED | APPLIED


5.2.5 Validation Agent
~~~~~~~~~~~~~~~~~~~~~~~
Deterministic safety rules have to be performed before sending MitigationActions to the analyst. This agent does not call any LLM.

  Completeness checks:
    Title should not be null.
    Description must be complete.
    Steps[] array must contain at least two items of length >=10.

  Safety checks (if matches exist, discard action):
    Dangerous system commands: del /f, format c:, dump database, and rm -rf
    Overly broad network rules: "block all" and "deny all ports"
    Proportional actions: "shutdown all," "delete all," and "disable all"
    Broad firewall rules with wildcards: 0.0.0.0/0 without specifying ports

  When all the above checks succeed:
    MitigationAction.validated = True
  Otherwise, cause(s) of failure are logged,
    and MitigationAction.validated = False.


5.3 Summary
------------
Details about all five agents in the system have been explained in this chapter, including the internal architecture, data format, and processing steps of all agents. Enrichment, which includes prompting for RAG augmented LLMs, Pattern Discovery with multi-factor similarity scoring, Mitigation, which involves chain-of-thought reasoning, and Validation are some significant design patterns.

Figure 5.2 shows the Sequence Diagram, illustrating the chronological
interaction between the Analyst, FastAPI server, and each agent during
an /api/ingest/instant call. The sequence shows: (1) the analyst sends a
POST request, (2) FastAPI calls the Ingestion Agent which returns a
ThreatEvent, (3) the Enrichment Agent queries ChromaDB and the LLM to
produce an EnrichedEvent, (4) the Pattern Agent clusters the event, (5)
the Mitigation Agent generates a MitigationAction, and (6) the Validation
Agent checks safety rules before returning the final result.

  [See Figure 5.2: Sequence Diagram — Threat Processing Flow]

Figure 5.3 shows the Activity Diagram (Flowchart), presenting the complete
pipeline decision logic. The flowchart includes the four key decision points:
duplicate check (discard if duplicate), enrichment confidence check (skip
store-back if confidence < 0.3), severity threshold check (log-only if
severity < 3), and validation check (flag and reject if safety rules fail).
Only events that pass all decision points are published to the SOC Dashboard.

  [See Figure 5.3: Activity Diagram — Pipeline Decision Logic]

The data models form a coherent pipeline chain:
  ThreatEvent -> EnrichedEvent -> ThreatPattern -> MitigationAction

Each stage's output is the next stage's input, enabling end-to-end
traceability for every event.
