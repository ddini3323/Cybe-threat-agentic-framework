================================================================================
CHAPTER 3 - SOFTWARE REQUIREMENT SPECIFICATION
================================================================================

3.1 Overall Description
------------------------

3.1.1 Product Perspective
~~~~~~~~~~~~~~~~~~~~~~~~~~

The system is a standalone, locally deployed Cyber Threat Intelligence (CTI)
automation platform. It operates independently of cloud services and integrates
with the analyst's existing workflow through a web browser-based dashboard.

The system interfaces with:
  - Local file system      : monitored input directory for CSV/JSON files
  - Ollama LLM runtime (local HTTP API on port 11434)
  - ChromaDB vector store (local persistent database)
  - External CTI feeds (Mastodon infosec.exchange - read-only polling)
  - Analyst browser (dashboard on port 8888)

The system is designed for single-analyst or small-team deployment within a
single organisation. It does not require any cloud infrastructure, external API
keys, or internet connectivity after initial setup (MITRE ATT&CK is cached
locally).


3.1.2 Product Functions
~~~~~~~~~~~~~~~~~~~~~~~~

The system performs the following primary functions:

  F1. Multi-source threat data ingestion (CSV, JSON, free text, live feeds)
  F2. Automatic normalisation into a unified ThreatEvent schema
  F3. LLM-based enrichment with RAG context from MITRE ATT&CK
  F4. Heuristic clustering of events into ThreatPatterns
  F5. Automated mitigation recommendation generation
  F6. Safety validation of generated mitigations
  F7. Human-in-the-loop approval/rejection of mitigations
  F8. Real-time 8-page SOC dashboard
  F9. Event flow tracing across all 5 pipeline stages
  F10. Live social media threat feed streaming


3.1.3 Constraints
~~~~~~~~~~~~~~~~~

  - All LLM inference must run locally (no cloud APIs permitted)
  - System must operate on hardware without a dedicated GPU
  - No external API keys required for core functionality
  - Dashboard must be accessible via standard web browser
  - LLM model size limited to models runnable with 8GB RAM


3.2 Specific Requirements
--------------------------

3.2.1 Functional Requirements
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

  FR-01 | The system shall poll the data/input/ directory every 5 seconds and
          automatically ingest any new CSV or JSON files.

  FR-02 | The system shall normalise all input formats into a unified ThreatEvent
          schema containing: event_id, timestamp, source, event_type, raw_text,
          indicator, severity, and raw_data fields.

  FR-03 | The system shall detect indicator types automatically using pattern
          matching: IP address, URL, Domain, Hash (MD5/SHA1/SHA256), CVE, Email.

  FR-04 | The system shall deduplicate events using MD5 hashing of source and
          data content to prevent reprocessing of identical indicators.

  FR-05 | The system shall enrich each ThreatEvent using a local LLM (llama3.2:3b
          via Ollama), extracting: IOCs, TTPs (MITRE IDs), CVEs, malware family,
          attack vector, affected assets, and enrichment confidence score.

  FR-06 | Before each enrichment LLM call, the system shall query ChromaDB for
          the top-5 most relevant MITRE ATT&CK techniques (cosine similarity
          >= 0.35) and inject them as context into the LLM prompt.

  FR-07 | The system shall store enriched events back into ChromaDB
          (threat_reports collection) to enable retrieval for future events.

  FR-08 | The system shall cluster enriched events into ThreatPattern objects
          using Jaccard similarity on TTP sets with a threshold of >= 0.7.

  FR-09 | The system shall generate structured mitigation recommendations (title,
          description, steps, sample_rule, priority 1-5) for events with
          severity >= 3 and for all newly discovered ThreatPatterns.

  FR-10 | The system shall validate all generated mitigations and reject rules
          that are overly broad (block all traffic), dangerous (disable firewall),
          or disproportionate (shutdown all systems).

  FR-11 | The system shall serve an 8-page web dashboard on port 8888 with
          auto-refresh every 3 seconds.

  FR-12 | The system shall provide a Flow Tracker page to trace any event through
          all 5 pipeline stages.

  FR-13 | The system shall provide a Live Input page accepting JSON, CSV, free
          text, and file uploads for manual threat submission.

  FR-14 | The system shall stream live threat data from Mastodon
          (infosec.exchange) public timeline with a 2-minute polling interval.

  FR-15 | All LLM processing shall execute on local hardware with no data
          transmitted to external services.


3.2.2 Performance Requirements
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

  PR-01 | Dashboard API responses shall complete within 500 milliseconds under
          normal operating conditions.

  PR-02 | The system shall process up to 5 events per enrichment cycle (one cycle
          every 5 seconds).

  PR-03 | ChromaDB semantic search queries shall complete within 200 milliseconds
          for a collection of 691 techniques.

  PR-04 | The system shall handle up to 500 stored events and 100 patterns without
          degradation in dashboard performance.

  PR-05 | The system shall remain responsive (dashboard accessible) during LLM
          inference calls of up to 300 seconds duration.


3.2.3 Software Requirements
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

  - Operating System   : Windows 10/11, Ubuntu 20.04+, or macOS 12+
  - Python             : Version 3.10 or higher
  - Ollama             : Latest version (local LLM runtime)
  - LLM Model          : llama3.2:3b (2GB, downloaded via ollama pull)
  - FastAPI            : >= 0.109.0 (web framework)
  - Uvicorn            : >= 0.27.0 (ASGI server)
  - ChromaDB           : >= 0.4.22 (vector database)
  - sentence-transformers: >= 2.3.1 (embedding model)
  - Pydantic           : >= 2.5.3 (data validation)
  - httpx              : >= 0.25.2 (async HTTP client)
  - Pandas             : >= 2.0.0 (data processing)
  - Web Browser        : Chrome, Edge, Firefox (any modern browser)


3.2.4 Hardware Requirements
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

  - Processor  : Intel Core i5 / AMD Ryzen 5 or higher - Required to handle
                 concurrent LLM inference (llama3.2:3b), ChromaDB vector search,
                 and the FastAPI web server simultaneously.

  - RAM        : Minimum 8 GB (Recommended 16 GB) - The LLM model requires
                 approximately 4GB during inference; remaining memory supports
                 ChromaDB, the FastAPI server, feed streaming, and OS overhead.

  - Storage    : Minimum 10 GB free (Recommended 20 GB SSD) - Accounts for the
                 LLM model (2GB), ChromaDB vector store (1GB), MITRE ATT&CK
                 dataset (500MB), Python dependencies (3GB), and runtime logs.

  - Internet   : Required on first run only to download the MITRE ATT&CK dataset
                 (~7MB from GitHub) and pull the Ollama LLM model (2GB). Also
                 required for live Mastodon feed streaming during operation.


3.2.5 User Requirements
~~~~~~~~~~~~~~~~~~~~~~~~

  UR-01 | The user shall be able to submit threat data via CSV, JSON, free text,
          or file upload through the web dashboard without any programming
          knowledge.

  UR-02 | The user shall be able to view all ingested events, enriched events,
          discovered patterns, and mitigations on separate, clearly labelled
          dashboard pages.

  UR-03 | The user shall be able to approve or reject AI-generated mitigations
          through the dashboard before they are marked as actionable.

  UR-04 | The user shall be able to trace any single threat event through all 5
          pipeline stages using the Flow Tracker page.

  UR-05 | The user shall be able to monitor real-time social media feed status
          and ingestion counts from the Feeds page.

  UR-06 | The user shall receive severity-classified alerts (LOW / MEDIUM / HIGH
          / CRITICAL / EMERGENCY) with colour-coded visual indicators.

  UR-07 | The user shall not require any programming knowledge to operate the
          system after initial setup.


3.2.6 Design Constraints
~~~~~~~~~~~~~~~~~~~~~~~~~

  DC-01 | The system must not transmit any threat data to external cloud services
          or APIs during normal operation.

  DC-02 | The system must use only open-source, freely available components with
          no licensing costs.

  DC-03 | The LLM model must be runnable on commodity hardware (8GB RAM, no GPU
          requirement).

  DC-04 | The web dashboard must function without JavaScript frameworks -
          vanilla HTML/CSS/JS only, ensuring compatibility with all modern
          browsers without build tooling.

  DC-05 | All data models must be validated using Pydantic v2 schemas to ensure
          type safety and consistent data contracts between agents.


3.3 Summary
------------

This chapter specified the complete requirements for the system across six
dimensions: product perspective, product functions, constraints, functional
requirements, performance requirements, and hardware/software requirements.

Key constraints driving the design are: local-only LLM execution for privacy,
commodity hardware compatibility, open-source components only, and human-in-the-
loop approval before any mitigation is marked actionable.

The 15 functional requirements (FR-01 through FR-15) define the complete
behaviour of the 5-agent pipeline, RAG subsystem, and dashboard. These
requirements are directly traceable to the implementation described in Chapter 5.
