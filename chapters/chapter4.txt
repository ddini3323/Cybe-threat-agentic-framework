4.1 Design Considerations
--------------------------

4.1.1 General Considerations
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Guidelines that helped determine the structure of the proposed solution included:

Privacy-first design:

All computations, from vector searches and embeddings to LLM inference and data storage, take place locally. Prompts, answers, and any threat intelligence data are not shared with third-party services. Each decision made about the technology has been affected by this architectural limitation.

Modularity:
Each stage of the pipeline has its own state, logging, and explicit input/output contract, implemented as a dedicated agent class.
    It provides an opportunity to swap, update, or test individual agents without interfering with the operation of other stages of the pipeline.
  
  Elegant Deterioration:
The process continues even without RAG knowledge in case there is failure in RAG initialization (say, the network is down for the initial MITRE download).
    Even in the event that the LLM fails to load, ingestion and pattern recognition continue.
    The system should not fall apart simply because one of its parts does.

  Human Oversight:
As opposed to being a wholly independent agent, the system is meant to serve as an aid in decision-making. Mitigations generated by the system are subject to verification before they can be labeled actionable.

Async First 
The web server must not be blocked by long running tasks (LLM inference, feed poll). The dashboard remains responsive during all LLM calls, which may run up to 30 to 90 seconds, by virtue of Python asyncio.


4.1.2 Development Methods
~~~~~~~~~~~~~~~~~~~~~~~~~~

  Development Methodology: Agile Incremental
Each individual agent went through independent design, development, and unit testing.
After each individual agent became part of the pipeline, integration testing occurred.
The dashboard and backend pipeline were developed simultaneously.

  First, Data Modeling
Prior to developing any of the agents, all of the data models for Pydantic—ThreatEvent, EnrichedEvent, ThreatPattern, MitigationAction, and AgentLogEntry—were developed. Right from the outset, this led to uniform data contracts throughout the pipeline.

  Testing-Driven RAG Development:
Prior to integrating it within the enrichment agent, the RAG subsystem was tested with semantic search queries such as (example query—"PowerShell malware execution" -> T1059.001 with a similarity score of 0.619).


4.2 Architecture Strategies
-----------------------------

4.2.1 Programming Language and Frameworks
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

 The choice of language of implementation was made from the following reasons:
    Strong web, machine learning, and security ecosystem
    Native concurrency and web server support using asyncio
    Quick validation of typed data using Pydantic v2
    Community help and documentation

  FastAPI was selected over Flask/Django because:
Built on top of ASGI (async-native), mandatory for non-blocking calls to LLMs
    Native Pydantic support, no need to validate requests/responses manually
    OpenAPI documentation created automatically for each of the 15 endpoints
    Uses Uvicorn, ASGI server, ready for deployment in production.

  ChromaDB was selected over Weaviate, Pinecone, and Qdrant because:
Completely runs locally; there is no need for cloud account/API keys
    Native support for sentence transformers
    Persistence without the need for an external DB server
    Lightweight enough to be deployed using only one computer

4.3 System Architecture
------------------------

The system follows a sequential multi-agent pipeline with three input channels,
five processing agents, a human approval layer, and a web dashboard.

Figure 4.1 illustrates the Use Case Diagram, showing the interactions between
the Security Analyst actor, the System Administrator actor, and the CTI Agentic
System boundary. The analyst interacts with six use cases: submitting threats,
viewing enriched events, viewing attack patterns, approving mitigations, running
benchmarks, and configuring feeds. The System Administrator manages feed
configuration and pipeline controls. The Live Feed actor (Mastodon) interacts
with the Submit Threat use case by providing real-time social media intelligence.

  [See Figure 4.1: Use Case Diagram]

through each agent to the analyst dashboard:

social media intelligence, and manual analyst input) converge at Agent 1.
The pipeline processes each ThreatEvent sequentially through five agents before
presenting the validated result to the analyst on the dashboard.

4.4.2 Data Flow Diagram - Level 1
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Figure 4.3 shows the DFD Level 1, expanding the system boundary into five
internal processes (P1–P5) and five data stores (D1–D5). Each process maps
directly to one pipeline agent. Process P1 (Ingestion) receives inputs from
all three external channels and writes normalised ThreatEvent objects to the
Event Queue (D1). P2 (Enrichment) reads from D1, queries ChromaDB (D3) for
MITRE context, calls the local LLM, and writes enriched results to the Events
Store (D2) and back to ChromaDB. P3 (Pattern Discovery) reads from D2 and
writes ThreatPattern objects to the Pattern Store (D4). P4 (Mitigation) reads
from D4 and writes MitigationAction objects to the Mitigations Store (D5).
P5 (Validation) reads from D5 and outputs the final validated result to the
analyst dashboard.

  [See Figure 4.3: DFD Level 1 — Internal Pipeline Flows]

  Processes:
    P1. Ingest and Normalise
    P2. Enrich with LLM + RAG
    P3. Discover Patterns
    P4. Generate Mitigations
    P5. Validate and Present

  Data Stores:
    D1. Event Queue (in-memory pending_events list)
    D2. Events Store (in-memory events list)
    D3. ChromaDB (mitre_techniques + threat_reports)
    D4. Patterns Store (in-memory patterns dict)
    D5. Mitigations Store (in-memory mitigations list)

  Flow:
    Live Feeds ------> P1 --> D1 (ThreatEvent queue)
    File System -----> P1 --> D1
    Analyst Input ---> P1 --> D1

    D1 --> P2 --> D2 (EnrichedEvent)
    D3 <--> P2 (RAG query + store back)

    D2 --> P3 --> D4 (ThreatPattern)

    D4 --> P4 --> D5 (MitigationAction)
    D2 --> P4 (high severity events)

    D5 --> P5 --> Analyst (APPROVED/REJECTED/PENDING)

    Analyst --> P5 (approve/reject decision)


4.4.3 Data Flow Diagram - Level 2 (Enrichment Agent Detail)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

  This level 2 DFD expands Process P2 (Enrichment Agent):

  Input: ThreatEvent (from Event Queue)

  Step 2.1 - Build Extraction Query
    ThreatEvent.raw_text --> query string

  Step 2.2 - RAG: Query MITRE ATT&CK
    query string --> ChromaDB (mitre_techniques)
    ChromaDB --> top-5 techniques (cosine similarity >= 0.35)
    techniques --> MITRE context string

  Step 2.3 - RAG: Query Past Threats
    query string --> ChromaDB (threat_reports)
    ChromaDB --> top-3 similar past events (similarity >= 0.35)
    past events --> similar threats context string

  Step 2.4 - Build LLM Prompt
    MITRE context string  \
    similar threats string +--> combined LLM prompt
    ThreatEvent details   /

  Step 2.5 - LLM Call (Ollama llama3.2:3b)
    LLM prompt --> Ollama API (local, port 11434)
    Ollama --> JSON response

  Step 2.6 - Parse and Validate
    JSON response --> Pydantic EnrichedEvent model
    Validation --> enrichment_confidence score

  Step 2.7 - Store Back to ChromaDB
    EnrichedEvent (if confidence > 0.3) --> ChromaDB (threat_reports)

  Output: EnrichedEvent --> Events Store + Pattern Discovery Agent

  Level 2 DFD - Mitigation Agent Detail:

  Input: ThreatPattern OR high-severity EnrichedEvent

  Step 4.1 - Determine Trigger
    EnrichedEvent.severity >= 3 ? --> generate for event
    New ThreatPattern discovered ? --> generate for pattern

  Step 4.2 - Build Mitigation Prompt
    Pattern/Event details --> structured prompt
    Fields included: name, severity, TTPs, IOCs, attack_vector,
                     affected_systems, malware_family

  Step 4.3 - LLM Call (Ollama llama3.2:3b)
    Mitigation prompt --> Ollama API
    Ollama --> JSON response

  Step 4.4 - Parse JSON Response
    JSON --> MitigationAction model
    Fields: title, description, steps[], sample_rule, priority

  Step 4.5 - Set Status
    MitigationAction.status = PENDING_REVIEW

  Output: MitigationAction --> Mitigations Store + Validation Agent


4.5 Summary
------------

The high-level architecture of the system was presented in this chapter across four dimensions:

  Design considerations: Human-in-the-loop, modular architecture, graceful degradation, privacy by design, and asynchronous first

  Architecture strategies: In pursuit of a local-first, asynchronous, open-source implementation, we decided to use Python 3.12 + FastAPI + ChromaDB

  System Architecture: Consists of a web dashboard, a RAG knowledge database, and a sequential pipeline of five agents operating on three different input channels: Manual, CTI feed, and social media (Mastodon)

  Data flow diagrams: Show how Level 0 contains external entities; Level 1 shows five processes and five data stores; and Level 2 covers RAG retrievals and enrichment & mitigation agent subprocesses

  The design ensures that all components are independently maintainable, the
  pipeline is source-agnostic (any input type enters the same normalisation
  stage), and the analyst retains control through the human-in-the-loop
  approval mechanism.
